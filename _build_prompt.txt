Project Overview
This is the single build reference for the CSOPESY Major Output: a CLI-based process
scheduler/multiplexer (the "CSOPESY Emulator") written in C++, modeled on Linux
screen , SLURM-style batch scripts, and PowerShell. It turns every requirement in the
handout into (1) a concrete project layout and (2) one consolidated build prompt that can
be handed to an AI coding agent or followed step by step directly — so nothing gets
missed before the Week 8 black-box quiz, where only config.txt may change between
test cases and recompiling is not allowed.

Scheduler Algorithms — FCFS & Round Robin
The scheduler runs continuously once initialize completes, one dispatch loop per
core, picked by the scheduler parameter:
FCFS (First-Come-First-Served): each process runs to completion, or until it hits
SLEEP, on whichever core frees up next, in ready-queue order. No preemption —
quantum-cycles has no effect.

Round Robin: each core runs its current process for up to quantum-cycles ticks, then
preempts it back onto the end of the ready queue even if unfinished, and pulls the next
ready process.
A process's lifecycle is the same under both algorithms: New → Ready → Running →
Finished , with two extra edges — Running → Ready (preempted at the end of a Round
Robin quantum) and Running → Sleeping → Ready (a SLEEP(X) instruction parks the
process for X ticks without holding a core, then returns it to the ready queue). The CPU
tick itself is just an integer incremented once per loop pass while the console is alive —
not wall-clock time.

# CSOPESY Emulator — Build Prompt
You are implementing a C++17 CLI program called the "CSOPESY Emulator": a 
process multiplexer and command-line scheduler. Follow every rule below 
exactly — grading is a black-box, timed quiz where only config.txt may be 
edited between test cases, with no recompiling, so behavior must match these 
specs precisely rather than approximately.
## 1. Startup & main menu
- On launch, print the ASCII banner (title, developer names, last-updated 
date) and a `root:\>` prompt.
- Recognize only `initialize` and `exit` before `initialize` has run. Any 
other command prints an error and re-prompts.
- `initialize` reads config.txt (space-separated key/value pairs: num-cpu, 
scheduler, quantum-cycles, batch-process-freq, min-ins, max-ins, delays-per-
exec), validates every value against its stated range, and constructs the 
Scheduler with that many Cores.
- After `initialize`, recognize: `screen`, `scheduler-start`, `scheduler-
stop`, `report-util`, `exit`.
## 2. screen command
- `screen -s <name>`: create a new Process `<name>` with a randomized 
instruction list (length uniformly random between min-ins and max-ins), 
enqueue it on the ready queue, clear the console, and attach to its screen.
- `screen -r <name>`: reattach to an existing, unfinished process's screen. 
If not found or finished, print exactly `Process <name> not found.` and stay 
on the main menu.
- `screen -ls`: print CPU utilization %, cores used, cores available, then 
"Running processes:" and "Finished processes:" sections.
- Inside a process's screen: `process-smi` shows name, ID, full print log 
(core + timestamp + message per line), current instruction line, total lines 
of code, and `Finished!` if done; `exit` returns to the main menu without 
killing the process.
## 3. Instruction set
Implement exactly these six instruction types, generated randomly (never 
typed by the user) within each process's instruction count:
- `PRINT(msg)` — log to the process's buffer; visible only through process-

smi. Default message `"Hello world from <process_name>!"` unless a test case

- `DECLARE(var, value)` — create a uint16_t variable.
- `ADD(var1, var2/value, var3/value)` — var1 = var2 + var3, clamped to [0, 
65535]; auto-declare undeclared operands at 0.
- `SUBTRACT(var1, var2/value, var3/value)` — same rules as ADD, clamped at 0

- `SLEEP(X)` (uint8_t X) — park the process off the core for X CPU ticks,

- `FOR([instructions], repeats)` — repeat a nested instruction block 
`repeats` times; support nesting up to exactly 3 levels.
Variables are process-local and persist until the process finishes.
## 4. Scheduler
- Build one thread per num-cpu core, pulling from a single mutex/condvar-
protected ready queue.
- scheduler == "fcfs": run each process to completion (or to its next SLEEP) 
with no preemption; quantum-cycles has no effect.
- scheduler == "rr": preempt the running process back to the end of the ready 
queue after quantum-cycles ticks if it hasn't finished.
- The CPU tick is a plain incrementing counter, advanced once per scheduler 
loop pass, independent of wall-clock time.
- delays-per-exec ticks of busy-wait happen before each instruction executes 
(0 = one instruction per tick).
## 5. scheduler-start / scheduler-stop
- scheduler-start: every batch-process-freq CPU ticks, spawn one new dummy 
process with a human-readable, unique name (e.g. p01, p02, …) and enqueue it, 
as long as the generator is running.
- scheduler-stop: stop spawning new processes; existing ones keep running to 
completion.
## 6. Reporting
- Implement one formatter that renders CPU utilization %, cores 
used/available, and the Running/Finished process tables.
- screen -ls prints it to the console; report-util appends it to csopesy-
log.txt and prints `Report generated at C:/csopesy-log.txt!`. Both running 
and finished processes must always be listed, for grading/debugging.
## 7. Non-functional constraints
- No command outside initialize/exit may run before initialize completes.
- Keep all behavior driven by config.txt, since the quiz format forbids 
recompiling between test cases — only parameters change.

Suggested Implementation Order
1. Config loader — parse config.txt into a Config struct, validate every range, unit-test
against the sample file.
2. CLI shell — main menu loop recognizing only initialize/exit pre-initialize, prints the
banner.
3. Process model — Process/PCB struct, Instruction base + the 6 instruction types,
variable table with clamped uint16_t arithmetic.
4. Instruction generator — randomized instruction lists within min-ins/max-ins, nested
FOR up to 3 levels.
5. Single-core FCFS scheduler — get one process running start-to-finish on one core
before adding concurrency.
6. Multi-core + threads — scale to num-cpu cores, each on its own thread, shared ready
queue behind a mutex/condvar.
7. Round robin — add quantum-cycles preemption and requeueing; verify against FCFS
by toggling scheduler in config.txt.
8. screen command — -s/-r/-ls, process-smi rendering, attach/detach, "Process <name>
not found." handling.
9. scheduler-start / scheduler-stop — batch-process-freq-driven generation of human-
readable process names.
10. report-util — reuse the screen -ls formatter, write to csopesy-log.txt.
11. Timing knobs — delays-per-exec busy-wait, SLEEP's tick-based wake-up; confirm the
CPU tick increments match the pseudocode.
12. Dry run against the quiz format — practice changing only config.txt between runs,
without recompiling, and recording one continuous, unedited .mp4 end to end.
